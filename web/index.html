AgniCalendar — one fire calendar, not three sensor counts

MODIS and VIIRS have watched Bangladesh burn for 20+ years, but the same fire was counted 2–5 times — once per satellite, once per pixel. AgniCalendar merges those repeat detections into one harmonized fire event, so March–April really can be compared with March–April, year after year.

The headline, in one line

What “harmonized” means here: vegetation detections (NASA FIRMS type 0) on the same UTC date whose centres are within 1.0 km belong to one fire event, regardless of sensor. FRP is never summed across sensors — MODIS pixels are ~1 km, VIIRS pixels ~375 m, so summing would double-count the same fire.

Harmonized burning activity calendar — events per month

Each cell is a harmonized fire event, not a raw pixel count. Darker = more burning. Outlined = critical month: more events than that month’s 2019–2024 average + 1 standard deviation. Anomalies are only shown for 2019–2024, when all three sensors were flying — earlier years get no anomaly rather than a misleading one.

Peak month in every one of the 22 years is March or April. The burning season is March–April; June–October is usually quiet — so a high June or October is unusual even when its absolute count is small.

Raw detections vs harmonized events, by year

Grey = raw FIRMS detections (the old way — the same fire counted many times). Orange = harmonized events (the calendar above). The gap is the double-counting this project removes. Yearly totals jump when VIIRS arrives (2013, 2019) because VIIRS sees smaller fires MODIS misses — that is sensor sensitivity, not proof burning increased.

Critical periods — unusual months worth a closer look

Anomaly z = (events − monthly average 2019–2024) ÷ standard deviation. “Critical” means events > average + 1 SD. Treat it as a flag for responders to check, not a verified emergency — with only 6 climatology years, the standard deviation itself is uncertain.

When to watch

How a responder / land manager would use this

  1. Before the season: look at March–April in the calendar — that is when Bangladesh burns, every year.
  2. During the season: compare this month’s harmonized events with the same month’s 2019–2024 average. Above average + 1 SD = critical, check it.
  3. After the season: do not compare a MODIS-only year (2003–2012) directly with a VIIRS year — the sensors see different fires. Compare within the same sensor era, or use the harmonized events.

Full code on GitHub ↗Method note

The Android app and FastAPI backend are in the same repository (app/ and backend/). This web page needs no login, no server and no APK — it reads the precomputed harmonized calendar. The API also serves it at GET /v1/harmonized/calendar.

Method & limitations — read before you quote a number

  • Data: NASA FIRMS yearly country files for Bangladesh — MODIS 2003–2024, VIIRS S-NPP 2013–2024, VIIRS NOAA-20 2019–2024. 40 files, 0 unavailable, 0 invalid rows. 2025–2026 yearly files are not published yet, so they are not in this calendar.
  • Only vegetation fires (FIRMS type 0) are harmonized. Static land sources (5,336), offshore (1,107) and volcano (0) are counted separately, never silently dropped.
  • Detections are pixels, not fires. 1 km / 1 UTC-day clustering is an approximation: a large fire can span several events, two nearby fires can merge, and a fire burning across midnight UTC is split in two.
  • Harmonized counts are still a lower bound — VIIRS sees smaller/cooler fires MODIS misses, and clouds, smoke and overpass timing leave gaps. A month with no detections is not evidence of no fire.
  • No cross-sensor FRP calibration is claimed. FRP is reported per sensor, never summed.
  • Reproduce it: python -m backend.processing.harmonize --years 2003-2024 --products modis,viirs-snpp,viirs-jpss1
