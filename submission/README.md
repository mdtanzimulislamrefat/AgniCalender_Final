## What to paste / link in the form

### 1. Project title
`AgniCalendar — One Harmonized Burning Activity Calendar for Bangladesh`

### 2. Project description (copy-paste, English)
> Satellites have watched Bangladesh burn for over 20 years, but the same fire was counted two to five times — once per satellite, once per pixel. MODIS reports far fewer detections than VIIRS, not because there are fewer fires, but because its 1 km pixels miss the smaller fires VIIRS sees at 375 m. Counting pixels therefore exaggerates burning whenever a new sensor arrives, and fire managers have no consistent picture of when burning really peaks.
>
> AgniCalendar fixes that by harmonizing the record. Vegetation detections (NASA FIRMS type 0) on the same UTC date whose centres are within 1.0 km belong to one fire event, regardless of sensor. FRP is never summed across sensors. From 244,308 raw FIRMS detections for Bangladesh (2003–2024) this produces 117,602 harmonized fire events — 2.08 detections per event. The peak month is April 2023 with 4,746 events. A monthly climatology (2019–2024, all three sensors flying) flags critical months where events exceed the same month's average by more than one standard deviation — for example January 2019 (z +1.94) and June 2023 (z +1.80, unusual for a normally quiet month).
>
> The result is a public web calendar any responder, scientist or land manager can open with no login: a year-by-month heatmap, raw-vs-harmonized yearly totals, and a critical-periods list, with the method and limitations stated on the page. The same harmonized calendar is also served by the project's FastAPI backend (`GET /v1/harmonized/calendar`) and in the Android app's season view. March–April is the burning season in all 22 years — that is when to watch, and an out-of-season spike is the signal that deserves a closer look.

## Judging — what this project is scored on
Impact, Creativity, Validity, Relevance, Presentation (1–5 each, at local → expert → executive phases). This pack is built for those five:
- **Relevance:** it answers the exact challenge sentence — a web app + harmonized burning activity calendar for a selected area.
- **Validity:** real FIRMS data, a stated method, anomalies only where the sensor mix matches the baseline, limitations on the page — not a claimed prediction.
- **Impact:** March–April season + critical-month flags a responder can actually use; Bangladesh-first, but the code takes any FIRMS country file.
- **Creativity:** the harmonization itself — 1 km / 1-day event merging, overlap share as a cross-check, per-sensor FRP.
- **Presentation:** the web demo opens in seconds with the headline numbers first; the 7 slides tell the same story in 7 pictures.

## Known limits — say them before a judge finds them
- 2025–2026 are not in the calendar (NASA has not published those yearly files yet).
- With only 6 climatology years (2019–2024), "critical" means "worth a closer look", not a verified emergency.
- A fire across midnight UTC is split into two events; a very large fire can span several events.
- The Android app still requires a login + local backend and its package id is still `com.example.simple_todo` — that is why the web demo, not the APK, is the submitted demo.
- Video generation was not used for the demo video script — record the 30-second video from the script with a phone / screen recording of the web demo.
